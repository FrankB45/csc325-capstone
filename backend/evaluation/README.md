# Git Gallery LLM Evaluation Suite

This isolated, standard-library-only suite evaluates Git Gallery's planned
repository analyses. It supplies a predefined task plus synthetic Git data to
the adapter; it does not model a chatbot, arbitrary questions, conversation
history, or follow-up clarification.

## Supported task scope

The README, Sprint 0 user stories, and project FAQ describe these AI analysis
areas:

- Explain visible differences between two selected screenshots.
- Group consecutive commits into related timeline milestones.
- Recommend representative, potentially visually significant commits for
  screenshot capture and review.

The user-requested “What changed in this commit?” case is included as a
commit-summary task based on supplied commit metadata and diff. This is a
reasonable evaluation task for repository analysis, but the exact production
task list/API is still for the team to confirm. Chat-like UI components also
exist in the prototype; this suite intentionally follows the clarified
predefined-task behavior instead of testing those chat components.

## Files

- `golden_set.json` — synthetic repository fixtures and independently authored
  expected task outputs.
- `system_prompt.txt` — proposed role, evidence rules, and task-specific
  output guidance.
- `llm_adapter.py` — the single integration point and deterministic mock
  adapter.
- `test_hallucination.py` — task-format and repository-grounding checks.
- `test_consistency.py` — compares repeated analyses by task semantics.
- `run_evaluation.py` — validates cases, calls the adapter, scores both checks,
  and returns an appropriate exit code.
- `test_evaluation_logic.py` — focused tests of factual checks and grouping
  consistency.

## Golden dataset format

Each case has a unique `id`, scenario `category`, selected `task` (task ID and
predefined question), `repository_data`, manually written `expected_output`,
`required_facts` and/or `required_behaviors`, optional
`required_limitations`, and `forbidden_claims`. Grouping cases may also define
`expected_groups`; recommendation cases may specify `expected_commit_ids`.
Fixtures use controlled synthetic hashes, timestamps, author labels,
changed-file lists, diffs, and screenshot observations. Expected outputs are
written in the dataset and are never generated by a model.

The cases cover single- and multi-file commits, added/deleted files, a
diff-supported bug fix, documentation-only change, vague and misleading
messages, incomplete diff, empty commit, similar and unrelated commit
sequences, misleadingly similar messages, different messages for similar
changes, one-commit and empty histories, a capture recommendation, and
screenshot comparisons with missing evidence.

## Checks and thresholds

### Hallucination / repository grounding

The threshold remains **90%**. The suite validates task-specific output shape;
checks the selected commit and exact changed-file list for commit summaries;
rejects unknown commit IDs; verifies groups cover the supplied history exactly
once, preserve consecutive spans, and match the reference groupings; checks
capture recommendations against known commits; checks structured author/date
and file references against fixture metadata; and matches case-specific
required facts, behaviors, and limitations while rejecting listed false
claims. Missing data must be recorded as a limitation, not answered by asking
a follow-up question.

The detector is deliberately lightweight: phrase variants are not a general
semantic judge, and it cannot reliably catch every fabricated statement in
free text (notably a fabricated author, timestamp, or unsupported claim that a
case did not anticipate). Exact file validation applies to the structured
`files_changed` field. Human review is needed when interpreting live-model
results.

### Consistency

Each case is submitted three times to the adapter with the same task and
repository data. The first response is reused for the grounding check. The
threshold remains **80%**, with all three outputs required to be substantively
equivalent and each output required to pass the grounding check.

- Commit summaries compare the target commit, changed-file set, major-change
  count, and expected facts.
- Grouping compares commit membership as unordered sets of groups and the
  rationale's expected factual signals; group titles and group order may
  differ.
- Recommendations compare recommended commit IDs as a set.
- Screenshot comparisons compare the number of changes, expected facts, and
  limitation signals.

This signature is a small fixture-based approximation; natural-language
rationales and subtle semantic changes still need review.

## Run the suite

From the repository root, run the full suite with one command:

```powershell
python backend\evaluation\run_evaluation.py
```

Default `mock` mode returns the independently authored expected outputs. Its
PASS result validates the runner and checks only; it is **not a real LLM
evaluation**. Real mode never falls back to mock:

```powershell
python backend\evaluation\run_evaluation.py --mode real
```

Run evaluation-logic tests:

```powershell
python -m unittest discover -s backend\evaluation -p "test_*.py" -v
```

## Task-specific output proposals and integration

The dataset currently represents four output shapes: commit summary
(`commit_sha`, `files_changed`, `summary`, `major_changes`, `limitations`),
grouping (`groups` with member IDs, title, rationale, plus limitations),
recommendations (recommended commit IDs, rationale, limitations), and
screenshot comparison (visible changes with before/after evidence and
limitations). These are evaluation proposals only—not a claimed production
schema. The teammate implementing the feature must confirm or adapt the task
IDs, request contract, and response fields before real integration.

Implement the real adapter in `llm_adapter.py` after that contract is agreed.
It should pass `case["task"]`, `case["repository_data"]`, and the system prompt
to the approved feature/provider, return its response text, keep credentials
outside source control, and surface integration errors. Do not modify the
teammate's unfinished implementation or silently use mock data for a real
request.
